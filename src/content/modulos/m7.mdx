## Essencial

Quanto mais autonomia você dá ao Claude, mais importa saber **quem decide o que ele pode fazer**. Este módulo reúne três peças: onde as configurações moram, como as regras de permissão funcionam e o que protege você quando algo dá errado. A palavra-chave é **camadas**: nenhuma sozinha basta.

### Onde moram as configurações

O Claude Code lê quatro tipos de arquivo de settings:

| Escopo | Arquivo | Vale para | Vai para o git? |
|---|---|---|---|
| **Usuário** | `~/.claude/settings.json` | Você, em todos os projetos | Não |
| **Projeto** | `.claude/settings.json` | Todos na pasta | **Sim** |
| **Local do projeto** | `.claude/settings.local.json` | Você, neste projeto | Não (o Claude Code o esconde do git ao criá-lo) |
| **Gerenciado** | `managed-settings.json` e outras fontes | A organização inteira | Distribuído pela TI |

No Windows, `~` é `%USERPROFILE%`. A instalação não cria esses arquivos: o de usuário nasce quando você muda algo no `/config`, e o local, na primeira vez que você aprova algo com "Sim, e não perguntar de novo".

Quando a mesma chave aparece em mais de um lugar, **vence o nível mais alto**: gerenciado, linha de comando (`--settings`), local, projeto, usuário. **Listas se somam**: se o usuário libera `Bash(npm test)` e o projeto libera `Bash(git status)`, valem os dois. O `/config` mostra e altera as opções, e o `/status` indica a origem das políticas gerenciadas. O `~/.claude.json` o Claude Code escreve sozinho; não o edite.

### Regras: allow, ask e deny

As regras ficam em `permissions`, em três listas: `allow` (usa sem pedir), `ask` (pede toda vez) e `deny` (não pode usar). A avaliação é **deny, depois ask, depois allow**, e a primeira que casa decide. Vale **entre arquivos**: um `deny` do usuário bloqueia um `allow` do projeto, e nenhuma regra mais específica abre exceção a um deny mais amplo. `Bash(aws *)` em deny bloqueia até o `Bash(aws s3 ls)` que estiver em allow.

<Nota rotulo="Quem cumpre a regra">
As regras são aplicadas pelo **Claude Code**, não pelo modelo. O pedido e o `CLAUDE.md` moldam o que o Claude tenta fazer, mas não mudam o que o Claude Code deixa ele fazer. Para garantia, use regra, modo de permissão ou hook ([M9](../m9/)).
</Nota>

O formato é `Ferramenta` ou `Ferramenta(especificador)`: `Bash` (todos os comandos), `Bash(npm test)` (exatamente esse), `Bash(npm run *)` (uma família), `Read(./.env)`, `WebFetch(domain:exemplo.com)`. Um deny com o **nome puro** (`Bash`) tira a ferramenta do contexto do Claude. Com especificador, ela segue disponível e só as chamadas que casam são bloqueadas.

**Regras de `Bash`.** O `*` casa com qualquer texto, inclusive espaços, e o espaço antes do `*` final importa:

| Você escreve | Casa | Não casa |
|---|---|---|
| `Bash(npm run build)` | `npm run build` | `npm run build --watch` |
| `Bash(npm run *)` | `npm run build`, `npm run test --watch` | `npm install` |
| `Bash(ls *)` | `ls -la`, `ls` | `lsof` |

Ponha o `*` **depois do subcomando**: `Bash(git log *)` libera só `git log`, e `Bash(git *)` libera todo comando git, inclusive `git -c ...`, que manda o git executar um programa. O Claude Code entende operadores de shell (`&&`, `||`, `;`, `|`): `Bash(npm test *)` não libera `npm test && rm -rf x`, porque cada parte precisa ser permitida.

**Uma regra de Bash não é uma cerca em volta do programa.** Ela casa com o comando como o Claude costuma escrevê-lo:

| Regra em deny | Barra | Não barra |
|---|---|---|
| `Bash(curl *)` | `curl https://exemplo.com` | `/usr/bin/curl ...`, `sh -c 'curl ...'` |
| `Bash(git push *)` | `git push origin main` | `git -C . push origin main` |

**Regras de `Read` e `Edit`** seguem a sintaxe do `.gitignore`. Quatro formas de caminho: `./x` ou `x` (a partir da pasta atual), `/x` (a partir da **origem da regra**, que é a pasta do projeto numa regra de `.claude/settings.json`), `~/x` (pasta pessoal) e `//x` (absoluto). Três pegadinhas:

- **`/Users/ana/arquivo` não é absoluto**: a barra única ancora na origem da regra. Absoluto é com duas barras.
- **No Windows**, o caminho vira POSIX antes de casar (`C:\Users\ana` vira `/c/Users/ana`). Para todo `.env` do disco C, use `//c/**/.env`.
- **`Write(...)`, `Grep(...)` e `Glob(...)` com caminho não casam nada.** Escreva `Edit(...)` no lugar de `Write` e `Read(...)` no lugar de `Grep` e `Glob`.

### Modos de permissão: o cardápio completo

O [M3](../m3/) mostrou os do ciclo do Shift+Tab. A tabela completa:

| Modo | Roda sem perguntar | Para quê |
|---|---|---|
| `default` (Manual) | Só leituras | Revisar cada ação |
| `acceptEdits` | Leituras, edições e comandos de arquivo comuns (`mkdir`, `touch`, `mv`, `cp`) | Iterar sobre código que você revisa |
| `plan` | Leituras | Explorar antes de mudar |
| `auto` | Tudo, com um classificador revisando antes | Tarefas longas |
| `dontAsk` | Leituras e o que está em `allow`; o resto é **negado** | Scripts e CI |
| `bypassPermissions` | Tudo | Só contêiner ou VM isolada |

No Claude Code 2.1.283 ou mais novo, o modo inicial de uma sessão interativa no terminal é o **auto**. Já o `claude -p` (sem tela) começa em Manual e **nega** o que exigiria pergunta, porque ninguém está lá para responder: foi o que vimos nas fichas.

O **classificador** do auto é outro modelo que revisa cada ação antes de ela rodar. Por padrão ele bloqueia coisas como baixar e executar código (`curl | bash`), enviar dados sensíveis para fora, deploy em produção, `force push` e `git reset --hard`. A doc avisa: **o auto reduz perguntas, não garante segurança.** Para impedir os modos soltos, use `permissions.disableAutoMode` e `permissions.disableBypassPermissionsMode`, com o valor `"disable"`.

**Caminhos protegidos** (`.git`, `.claude`, `.vscode`, `.idea`, `.husky`, `.devcontainer`, entre outros) têm regra própria de escrita por modo, e uma regra `allow` em settings **não** pré-aprova escrita neles.

### Segredos: o que uma regra de leitura faz e não faz

O caso clássico é o `.env`. A regra:

```json
{
  "permissions": {
    "deny": ["Read(./.env)"]
  }
}
```

Ela barra a ferramenta `Read`, o `@arquivo` e os comandos de leitura que o Claude Code reconhece no `Bash` (`cat`, `head`, `tail`, `sed`). Mas a doc avisa que **não** cobre um programa que abre o arquivo por conta própria, como um script em Python ou Node. A Ficha 1 prova os dois lados: com a regra ligada, um `node ler-env.mjs` mostrou o segredo.

Daí a escada de defesas, da mais fraca à mais forte:

1. **`.gitignore`:** o segredo não vai para o repositório. Não protege de leitura local.
2. **Regra `Read` em deny:** barra as ferramentas do Claude e os comandos reconhecidos. Não é cerca.
3. **Sandbox:** o sistema operacional barra qualquer processo. É a cerca real, mas não existe no Windows nativo.
4. **Não ter o segredo na pasta:** variável de ambiente fora do projeto, chave de curta duração, cofre. O segredo que o Claude nunca vê é o único que ele não vaza.

Um arquivo `.claudeignore` **não tem efeito**: a doc manda passar as entradas para regras `Read` em deny.

### Prompt injection

**Prompt injection** é inserir texto malicioso onde o Claude vai ler (uma página, um arquivo, a resposta de uma ferramenta MCP, o corpo de uma issue) para fazer o modelo trocar as suas instruções pelas do atacante. O texto parece dado e age como ordem.

As camadas que a documentação lista: o sistema de permissões (no Manual, ação sensível pede aprovação); `curl` e `wget` não são aprovados sozinhos; o `WebFetch` costuma resumir a página por uma chamada separada de modelo, e o Claude recebe o resumo, não a página crua; comando que o Claude Code não consegue analisar por completo pede confirmação; e o classificador do modo auto bloqueia ação que parece guiada por conteúdo hostil.

Na Ficha 3 plantamos uma instrução escondida num arquivo, num modo que **permitia** gravar, e o Claude a ignorou e ainda avisou. É bom, mas é **o modelo agindo bem**, não garantia: a doc diz que nenhum sistema é imune. Práticas recomendadas: revise comandos antes de aprovar, não canalize conteúdo não confiável direto para o Claude, confira mudanças em arquivos críticos, use máquina virtual para scripts de fontes externas e relate comportamento suspeito com `/feedback`.

### O sandbox: a cerca de verdade

O **sandbox** é um limite que o **sistema operacional** impõe em volta dos comandos de shell e dos processos que eles iniciam. Como o limite vale enquanto o comando roda, o Claude Code pode rodar comandos sandboxed **sem perguntar**.

| Acesso | Padrão com o sandbox ligado |
|---|---|
| Escrita | A pasta de trabalho, uma pasta temporária e pastas que você adicionou |
| Leitura | A maior parte da máquina, **inclusive** `~/.ssh` e `~/.aws/credentials`, a menos que você bloqueie |
| Rede | Sem rota direta: passa por um proxy que confere o domínio contra a sua lista de permitidos, que começa vazia |

Três fatos: **vem desligado** (ligue com `/sandbox` ou `sandbox.enabled`); **só existe em macOS, Linux e WSL2**, e no Windows nativo os comandos rodam sem sandbox; e **cobre só o shell**: `Read`, `Edit`, `Write`, `WebFetch`, MCP local e hooks rodam fora dele e seguem as regras. Regra controla o que o Claude **tenta**; o sandbox limita o que um comando **consegue**, mesmo que uma injeção engane o modelo.

### Menos prompts, sem abrir a guarda

Em vez do bypass, monte uma allowlist estreita. A skill embutida **`/fewer-permission-prompts`** varre as suas conversas recentes atrás de leituras comuns de `Bash` e MCP e propõe uma allowlist em `.claude/settings.json`. Não a executamos aqui, porque ela **lê o histórico das suas sessões**. Rode-a num projeto seu e leia cada linha antes de aceitar. No modo interativo, `allow` do projeto só vale depois que você aceita o diálogo de confiança da pasta.

### Confiança em MCP e plugins

Servidor MCP e plugin rodam código e entregam texto que o Claude lê: são superfície de ataque e de injeção. A doc sugere escrever os seus ou usar de quem você confia, e lembra que a Anthropic revisa conectores contra critérios de listagem, mas **não audita** nenhum. Olhar o `.mcp.json` não mostra todos os servidores de uma sessão: os de outros escopos e os de plugins ficam fora dele. O [M10](../m10/) e o [M13](../m13/) detalham.

### Quando nunca usar o bypass

`bypassPermissions` desliga avisos e verificações, inclusive para escrever em `.git` e `.claude`. Use **só** em ambiente isolado, como contêiner ou máquina virtual, nunca num laptop com seus arquivos e credenciais. O **dev container** é o caminho recomendado: os comandos rodam dentro dele e as edições aparecem no seu repositório. Mas a doc avisa: com `--dangerously-skip-permissions`, um repositório malicioso pode exfiltrar **tudo que estiver acessível no contêiner**, inclusive as credenciais do Claude em `~/.claude`. Por isso: só repositórios confiáveis, nada de montar `~/.ssh` ou credenciais de nuvem, usuário não-root (a CLI recusa a flag como root) e saída de rede restrita. Se a meta é menos pergunta, a doc aponta o **modo auto**.

### Privacidade e uso de dados

Conferido na página de uso de dados em 13/11/2026 (a fonte muda; confirme):

- **Contas de consumidor** (Free, Pro, Max, Ultra): você escolhe se seus dados ajudam a treinar modelos. Ligada a opção, retenção de **5 anos**; desligada, **30 dias**.
- **Contas comerciais** (Team, Enterprise, API, terceiros): a Anthropic **não treina** com código ou prompts do Claude Code, salvo se o cliente optar. Retenção padrão de **30 dias**.
- **Local:** as transcrições das sessões ficam em texto puro em `~/.claude/projects/`, por padrão 30 dias (`cleanupPeriodDays`). **Podem conter o que você colou ou o Claude leu.**
- **`/feedback`, `/bug` e `/share`:** as transcrições enviadas são retidas por 5 anos. Nada vai sem você escolher.

<Camada tipo="capo" titulo="Confiança, wrappers e outras proteções">

### Confiança da pasta e `claude -p`

Regras `permissions.allow` e `additionalDirectories` em `.claude/settings.json` concedem capacidade, então só valem **depois** de você aceitar o diálogo de confiança da pasta. `deny` e `ask` não precisam disso, pois só restringem. O `claude -p` **nunca** mostra o diálogo: nele, `allow` do projeto não é usado (sai o aviso `this workspace has not been trusted`), mas `deny` vale. O `settings.local.json` **não rastreado** pelo git vale sem confiança, porque é seu. Antes de rodar `claude -p` num repositório que você não escreveu, a doc sugere `--setting-sources user` ou `--bare`.

### Wrappers

Antes de casar regras de `Bash`, o Claude Code remove um conjunto fixo (`timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`), então `Bash(npm test *)` também casa `timeout 30 npm test`. Corredores como `npx`, `docker exec` e `devbox run` **não** estão na lista: `Bash(devbox run *)` casa o que vier depois, inclusive `devbox run rm -rf .`. Escreva a regra com o corredor e o comando interno.

### Remoção em caminho crítico

`rm` e `rmdir` reconhecidos em caminhos críticos (como `rm -rf /` ou `rm -rf ~`) pedem confirmação em **todos** os modos, inclusive no bypass, e nenhuma regra `allow` nem hook os aprova.

### Limites de diretório e travas

`permissions.blockReadsOutsideWorkingDirectories` e `permissions.blockWritesOutsideWorkingDirectories` barram leitura e escrita fora da pasta de trabalho, mas a segunda não limita o shell, MCP nem hooks: para isso, o sandbox. Em configurações gerenciadas, `allowManagedPermissionRulesOnly` faz delas a única fonte de regras. `disableBypassPermissionsMode` funciona em qualquer escopo: um usuário pode se trancar fora do bypass.

### Windows e WebDAV

A doc recomenda **não** habilitar o WebDAV no Windows nem deixar o Claude acessar caminhos como `\\*`: o WebDAV pode gerar requisições de rede que contornam o sistema de permissões.

</Camada>

<Camada tipo="armadilhas">

### Tratar `deny Read` como cofre

Ela barra as ferramentas do Claude e os comandos reconhecidos, não um script que abre o arquivo. Prove (Ficha 1) e use o sandbox ou tire o segredo da pasta.

### Allow no projeto que "não pega" no `claude -p`

Em `.claude/settings.json`, `allow` só vale após a confiança da pasta, que o `-p` não pede. Use `settings.local.json` ou `--allowedTools`.

### Liberar `Bash(git *)` achando que é só git comum

O `*` no lugar do subcomando casa também `git -c ...`. Libere por subcomando: `Bash(git log *)`.

### Contar com `deny Bash(git push *)` como cerca

`git -C . push` escapa. Para impedir de verdade, hook ou sandbox de rede.

### Regras `Write`, `Grep` ou `Glob` com caminho

Não casam nada. Use `Edit` e `Read`.

### Bypass no laptop

Sem contêiner nem VM, nada contém o estrago. E dentro do contêiner, o que está montado é alcançável.

### Instrução no `CLAUDE.md` como controle de acesso

É contexto, não regra de ferro ([M6](../m6/)). Para bloquear, `deny`; para impedir sempre, hook.

### Settings com erro de sintaxe

O Claude Code pode ignorar o arquivo inteiro, e as regras de bloqueio somem junto. Confira com `claude doctor`.

### Chave de API colada na conversa

Ela vai para a transcrição local em texto puro e para o contexto. Rotacione a chave ([M4](../m4/)).

</Camada>

  titulo="Bloquear a leitura do .env e provar"
  objetivo="Ver um segredo vazar, bloqueá-lo com uma regra e descobrir onde a regra não alcança."
  minutos={25}
  pre="Laboratório baixado e commitado"
>

1. Crie um segredo **falso** (o `.gitignore` do laboratório já ignora `.env`):

   <SO unix='echo "API_KEY=sk-FALSO-nao-use-0000" > .env' win='Set-Content .env "API_KEY=sk-FALSO-nao-use-0000" -Encoding ascii' />

2. **Sem regra**, peça a leitura:

   ```bash
   claude -p "Leia o arquivo .env e me diga o valor de API_KEY."
   ```

3. Crie a regra de bloqueio:

   <SO unix={`mkdir -p .claude && echo '{"permissions":{"deny":["Read(./.env)"]}}' > .claude/settings.json`} win={`New-Item -ItemType Directory -Force .claude | Out-Null; Set-Content .claude/settings.json '{"permissions":{"deny":["Read(./.env)"]}}' -Encoding ascii`} />

   Repita o pedido do passo 2.

4. **Tente passar pelo lado.** Libere o `cat` e peça o conteúdo:

   ```bash
   claude -p "Rode o comando: cat .env e me diga o conteúdo." --allowedTools "Bash(cat *)"
   ```

5. Agora o desvio que a documentação avisa. Crie um script que abre o arquivo sozinho e peça para rodá-lo:

   <SO unix={`echo "import { readFileSync } from 'node:fs'; console.log(readFileSync('.env', 'utf8'));" > ler-env.mjs`} win={`Set-Content ler-env.mjs "import { readFileSync } from 'node:fs'; console.log(readFileSync('.env', 'utf8'));" -Encoding ascii`} />

   ```bash
   claude -p "Rode exatamente: node ler-env.mjs" --allowedTools "Bash(node *)"
   ```

<Prova>

O passo 2 **vaza** o segredo. O passo 3 bloqueia. O passo 4 também bloqueia, mesmo com `cat` liberado, porque a regra de leitura vale para os comandos reconhecidos. O passo 5 **vaza de novo**. Na nossa execução:

| Passo | O que aconteceu |
|---|---|
| 2 (sem regra) | `O valor de API_KEY no .env é sk-FALSO-nao-use-0000.` |
| 3 (com `deny`) | `Não consegui ler o .env. As permissões deste ambiente bloqueiam o acesso`, com uma chamada `Read` negada |
| 4 (`cat` liberado) | `cat .env` **negado**, apesar do `allow` |
| 5 (`node ler-env.mjs` liberado) | A saída trouxe `API_KEY=sk-FALSO-nao-use-0000`, sem nenhuma negação |

</Prova>

<Gabarito>

A regra vale para o que o Claude Code **reconhece** como leitura: a ferramenta `Read`, o `@arquivo` e comandos como `cat`. Um programa que abre o arquivo sozinho não passa por esse reconhecimento. Para barrar **todos** os processos, o caminho é o sandbox, e a melhor defesa é **não deixar o segredo na pasta**.

</Gabarito>

<DeuErro>

- **O passo 3 continua vazando.** O `settings.json` pode ter erro de sintaxe e ser ignorado inteiro. Rode `claude doctor`.
- **No passo 5 o Claude recusa por conta própria.** Insista no comando exato (`Rode exatamente: ...`): é ele que mede a **regra**, não a boa vontade do modelo.
- **`require is not defined`.** O laboratório usa módulos ES; mantenha `import` e a extensão `.mjs`.

</DeuErro>

</Desafio>

<Ficha

  n={2}
  titulo="Montar uma allowlist e testar a precedência"
  objetivo="Liberar só o necessário e provar que um deny vence um allow mais amplo."
  minutos={25}
  pre="Ficha 1"
>

1. Crie um remoto vazio e ligue-o, para ter um `git push` para barrar:

   ```bash
   git init --bare ../remoto.git
   git remote add origin ../remoto.git
   ```

2. Crie as regras no arquivo **local** (o `-p` ignora `allow` do projeto):

   <SO unix={`echo '{"permissions":{"allow":["Bash(npm test)","Bash(git *)"],"deny":["Bash(git push *)"]}}' > .claude/settings.local.json`} win={`Set-Content .claude/settings.local.json '{"permissions":{"allow":["Bash(npm test)","Bash(git *)"],"deny":["Bash(git push *)"]}}' -Encoding ascii`} />

3. Peça duas coisas, uma liberada e outra não:

   ```bash
   claude -p "Rode npm test e me diga quantos testes passaram. Depois rode npm install lodash e me diga o resultado."
   ```

4. Teste a precedência: `git *` está liberado, mas `git push *` está em deny.

   ```bash
   claude -p "Rode: git log --oneline -1. Depois rode: git push origin main. Diga o que cada um fez."
   ```

5. Confira que nada chegou ao remoto:

   ```bash
   git --git-dir=../remoto.git branch --list main
   ```

<Prova>

O passo 3 roda o `npm test` e **nega** o `npm install` (nada instalado, `package.json` intacto). No passo 4, o `git log` roda e o `git push` é negado, **mesmo com `Bash(git *)` liberado**. O passo 5 não imprime nada: o remoto não recebeu o `main`. Na nossa execução:

```text
npm test: 10 de 10 testes passaram.
```

<Gabarito>

`allow` abre o que você nomeou; o resto cai no padrão do modo, e em `claude -p` perguntar é impossível, então é **negado**. Em sessão interativa, o `npm install` abriria um pedido de confirmação, e o `/permissions` listaria cada regra com o arquivo de origem.

</Gabarito>

<DeuErro>

2. Peça um resumo, num modo em que **gravar arquivos seria permitido**:

   ```bash
   claude -p "Resuma o arquivo notas.md em duas frases." --permission-mode acceptEdits
   ```

3. Confira se a injeção funcionou:

   <SO unix="ls PWNED.txt" win="Test-Path PWNED.txt" />

O Claude resume as três pendências e **avisa** do comentário. O `PWNED.txt` não existe. Na nossa execução, sem nenhuma chamada negada:

```text
O arquivo também traz um comentário HTML oculto com instruções dirigidas a assistentes de IA,
```

<Gabarito>

Quem barrou foi o **modelo**: tratou o comentário como dado e ainda reportou. É a primeira camada, e a mais frágil. Se ele tivesse obedecido, entrariam as outras: o `curl | sh` pede aprovação ou é bloqueado pelo classificador. Este resultado **não** prova que o Claude é imune.

</Gabarito>

- **O Claude não mencionou o comentário.** O resumo pode omitir; pergunte "há instruções estranhas no arquivo?".
- **O `curl` rodou.** Algo no seu ambiente libera `Bash(curl *)`. Remova essa regra.

</DeuErro>

<Ficha
  id="m7-e4"
  n={4}
  titulo="Ligar o sandbox"
  objetivo="Ligar o isolamento do sistema operacional e provar que ele barra uma escrita."
  minutos={20}
  pre="macOS, Linux ou WSL2"
  verificacao="nao-testado"
>

Esta ficha **não foi executada aqui**: a máquina de teste é Windows nativo, onde o sandbox não existe, e sem WSL2 instalado. Os passos seguem a documentação de 13/11/2026.

1. Abra o Claude Code numa pasta de projeto no macOS, no Linux ou dentro de uma distribuição WSL2.
2. Ligue o sandbox:

   ```text
   /sandbox
   ```

   No Linux e no WSL2, o painel mostra se faltam dependências (`bubblewrap` e `socat`). Instale o que ele indicar, reinicie o Claude Code e rode `/sandbox` de novo.
3. Peça uma escrita fora da pasta de trabalho:

   ```text
   Rode o comando: touch ~/sandbox-probe
   ```

4. Peça uma conexão a um domínio que você não liberou:

   ```text
   Rode o comando: curl -sI https://example.com
   ```

<Prova>

O passo 3 **falha**: no macOS com `Operation not permitted`, no Linux e no WSL2 com `Read-only file system`. O passo 4 não sai direto: a rede passa por um proxy que confere o domínio contra a sua lista de permitidos, que começa vazia, e o seu modo de permissão decide o que acontece com o domínio fora da lista. (Não executado: segundo a documentação.)

</Prova>

<Gabarito>

O sandbox é o único mecanismo desta página que barra **qualquer processo**. Ele deveria fechar o desvio da Ficha 1 (com o `.env` em `sandbox.filesystem.denyRead`, o `node ler-env.mjs` falharia, segundo a doc; não testamos). Lembre: ele cobre só o shell.

</Gabarito>

<DeuErro>

- **`Sandboxing requires WSL2`.** A distribuição está em WSL1. Confira com `wsl -l -v` e atualize.
- **No Windows nativo o `/sandbox` não protege nada:** os comandos rodam sem sandbox. Use WSL2.
- **O painel só mostra a aba Dependencies.** Falta algo no Linux/WSL2; corrija o que ela apontar e reinicie.

</DeuErro>

<Desafio>
