## Essencial

Até aqui, tudo que você fez mora no seu computador. Este módulo leva uma página para um endereço que qualquer pessoa abre. É o passo que transforma exercício em entrega.

### O que é um site estático

Um **site estático** é uma pasta com arquivos prontos: HTML, CSS, JavaScript, imagens. O servidor só os entrega, do jeito que estão. Não roda código seu, não consulta banco, não guarda cadastro.

Isso cobre mais do que parece: portfólio, landing page, documentação, este curso. Quando você precisar de login, banco ou formulário que grava dados, entra o servidor, e o [M20](../m20/) trata disso. A boa notícia é que o estático é a hospedagem mais barata que existe, porque é o trabalho mais simples para quem hospeda.

**Build** é a etapa que transforma o seu projeto nessa pasta final. O site do [M1](../m1/) não precisa: o `index.html` já é a pasta. Projetos com framework (como o deste curso) rodam um comando, `npm run build`, que gera uma pasta pronta (aqui, `dist/`). **Só essa pasta vai para a internet.**

### Onde publicar de graça

Quatro opções comuns, conferidas na documentação de cada uma em 13/11/2026:

| Hospedagem | Grátis? | Prévias de PR | Voltar a versão anterior |
|---|---|---|---|
| **GitHub Pages** | Sim, para repositórios públicos. Repositório privado depende do seu plano | Não nativas | Revert do commit e novo deploy |
| **Cloudflare Pages** | Sim, no plano Free (500 builds por mês; até 20.000 arquivos por site; 25 MiB por arquivo) | Sim, sem limite de prévias ativas | Rollback instantâneo para um deploy de produção anterior |
| **Netlify** | Consulte o plano atual na página de preços | Sim (*Deploy Preview*, uma por PR) | **Publish Deploy** em qualquer deploy bem-sucedido |
| **Vercel** | Consulte o plano atual na página de preços | Sim | Instant Rollback; no plano Hobby, só para o deploy imediatamente anterior |

A página inicial do Cloudflare Pages traz um aviso que pergunta se você tem certeza de que quer usar o Pages e recomenda o Workers para projetos novos. Confira esse aviso antes de escolher.

O curso usa o **GitHub Pages**: você já tem a conta, o repositório e o `gh` do [M4](../m4/). E o site deste manual foi montado para ser publicado assim.

Duas ressalvas do GitHub Pages, ambas da documentação:

- **É estático e não é para negócio.** A própria página de limites diz que o serviço não deve ser usado como hospedagem gratuita para rodar loja virtual ou software como serviço, nem para transações sensíveis.
- **Tem tetos.** Site publicado de até 1 GB, tráfego mensal de cerca de 100 GB (limite brando), deploy que passa de 10 minutos é cancelado.

<Nota rotulo="Para um cliente de verdade">
Projeto comercial pede hospedagem de plano pago ou um provedor cujos termos aceitem uso comercial. Leia os termos antes de prometer o endereço. O [C4](../c4/) volta a isso.
</Nota>

### Publicar no GitHub Pages, passo a passo

O GitHub Pages publica de dois jeitos, que você escolhe em **Settings, Pages, Build and deployment, Source**:

| Modo | O que faz | Quando |
|---|---|---|
| **Deploy from a branch** | Publica uma pasta de um branch (a raiz ou `/docs`) a cada push | Site que já é HTML pronto |
| **GitHub Actions** | Um workflow constrói e publica | Projeto com build. É o que o curso usa |

O caminho com Actions tem quatro peças, e o Claude escreve a terceira para você:

1. Um repositório no GitHub com o projeto (o `gh repo create` do [M4](../m4/)).
2. **Settings, Pages, Source: GitHub Actions.**
3. Um arquivo `.github/workflows/pages.yml`. Peça: "crie o workflow que publica esta pasta no GitHub Pages por GitHub Actions".
4. Um `git push` no `main`.

O workflow precisa de três permissões, e a documentação exige no mínimo `pages: write` e `id-token: write` no job de deploy:

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

Ele usa três ações oficiais: `actions/configure-pages`, `actions/upload-pages-artifact` e `actions/deploy-pages`. O ambiente se chama `github-pages`.

Quando o push termina, a aba **Actions** mostra a execução. Verde, o site está no ar em:

```text
https://SEU-USUARIO.github.io/NOME-DO-REPOSITORIO/
```

**Atenção ao caminho.** Num repositório comum, o site vive **dentro** de `/NOME-DO-REPOSITORIO/`, não na raiz. Um link escrito como `/estilo.css` procura `usuario.github.io/estilo.css` e quebra. Sites com framework resolvem isso configurando o caminho-base. O deste curso faz isso no `astro.config.mjs` (`base: '/curso-claude-code'`).

### Domínio e DNS

O endereço `usuario.github.io` é um **subdomínio grátis**. Serve para portfólio e estudo. Para um cliente, você quer `meunegocio.com.br`.

Um **domínio próprio** se registra, por ano, num registrador. O preço varia por extensão e por registrador: consulte o do registrador que escolher, sem confiar em número de blog. Depois, você aponta o domínio para o GitHub criando registros no **DNS**, a "lista telefônica" que traduz nomes em endereços.

| Quer usar | Crie este registro | Valor |
|---|---|---|
| `www.meunegocio.com.br` (recomendado pela própria doc) | `CNAME` em `www` | `SEU-USUARIO.github.io` |
| `meunegocio.com.br` (domínio raiz) | quatro `A` em `@` | `185.199.108.153`, `185.199.109.153`, `185.199.110.153`, `185.199.111.153` |
| O mesmo, em IPv6 | quatro `AAAA` em `@` | `2606:50c0:8000::153` a `2606:50c0:8003::153` |

Depois, em **Settings, Pages, Custom domain**, informe o domínio. Registros novos levam de minutos a horas para valer em toda a internet, e isso se chama **propagação**.

Você confere o DNS de fora, sem painel nenhum:

```bash
nslookup pages.github.com
```

### HTTPS

**HTTPS** é o cadeado: o tráfego vai cifrado e o navegador confia no site. No GitHub Pages ele vem pronto: todo site tem suporte, e nos domínios próprios o GitHub pede o certificado à Let's Encrypt depois que o DNS confere. Ligue a opção **Enforce HTTPS**, em Settings, Pages, para redirecionar todo acesso `http://` para `https://`.

Um erro típico: página em HTTPS que carrega imagem ou script por `http://` (conteúdo misto). O navegador bloqueia ou avisa. Troque os endereços por `https://`.

### O que vai para o navegador é público

Num site estático, **todo arquivo publicado é legível por qualquer pessoa**: abra "Ver código-fonte" em qualquer página. Isso inclui qualquer valor que o build tenha embutido no JavaScript.

Por isso:

- **Chave de API no código do site não é segredo.** Quem abre o site a vê. Chaves que dão acesso a dinheiro ou a dados ficam em um servidor ou função (a documentação da Netlify manda usar função serverless ou edge para valores sensíveis). O [M20](../m20/) mostra como.
- **Segredo só do build** (um token para baixar dados antes de gerar as páginas) mora nos **segredos do repositório**: Settings, Secrets and variables, Actions, New repository secret. Pela linha de comando, `gh secret set NOME`. No workflow, o valor entra com `${{ secrets.NOME }}`.
- **Configuração não secreta** (um nome de site, um endereço de API pública) vai em **variáveis**, na aba Variables do mesmo lugar, e entra com `${{ vars.NOME }}`.

Dois detalhes de segurança que a documentação do GitHub dá: os segredos **não** são passados a workflows disparados por fork (a exceção é o `GITHUB_TOKEN`), e não são passados a eventos do Dependabot.

### Prévias e voltar atrás

Uma **prévia** (*preview*) é uma cópia temporária do site para cada pull request, com endereço próprio, para você ver antes de publicar. Cloudflare Pages, Netlify e Vercel fazem isso sozinhos. No GitHub Pages não há prévia nativa: veja a mudança localmente (`npm run preview`) antes do merge.

**Voltar atrás** (*rollback*) é a rede de segurança do deploy. Cada hospedagem tem o seu jeito:

| Hospedagem | Como volta |
|---|---|
| GitHub Pages | `git revert` do commit ruim e push. O workflow publica a versão anterior (o [M4](../m4/) ensinou o `revert`) |
| Cloudflare Pages | Rollback para um deploy de produção anterior. Prévias não servem de alvo |
| Netlify | **Publish Deploy** num deploy anterior. Um novo push no repositório **sobrescreve** o rollback |
| Vercel | Instant Rollback. Ele desliga a atribuição automática dos domínios de produção, então novos pushes não entram no ar até você desfazer o rollback |

### Medir visitas sem rastrear gente

Para saber se alguém visita seu site, você não precisa de cookies nem de banner de consentimento. Duas opções que descrevem a si mesmas como respeitosas com a privacidade:

- **Cloudflare Web Analytics**: a documentação o descreve como análise "privacy-first", sem exigir mudança de DNS nem o proxy da Cloudflare. A página não diz se é gratuito nem se usa cookies: confira no painel antes de afirmar algo ao cliente.
- **GoatCounter**: código aberto, gratuito para "uso público razoável", e identifica visitas **sem cookies** e sem identificadores únicos.

Em ambos, o princípio é o mesmo: contar visitas, não pessoas.

### Site de usuário e site de projeto

O repositório chamado `SEU-USUARIO.github.io` vira o site raiz da conta (`https://SEU-USUARIO.github.io/`), e a documentação limita a um site de usuário por conta. Qualquer outro repositório vira um **site de projeto**, sob `/NOME-DO-REPOSITORIO/`.

### Limites de build do GitHub Pages

O limite de "10 builds por hora" descrito na documentação **não vale** para quem publica por um workflow próprio do GitHub Actions. Excesso de requisições a um site Pages devolve o erro HTTP 429.

### Versões das ações

A documentação do GitHub, em 13/11/2026, mostra `actions/configure-pages@v5`, `actions/upload-pages-artifact@v4` e `actions/deploy-pages@v4`. O workflow que o Claude gerou na nossa execução usou `upload-pages-artifact@v3`, uma versão mais velha. Funciona até a versão antiga ser descontinuada. **Peça ao Claude para conferir as versões atuais na documentação**, ou compare com a página "Using custom workflows with GitHub Pages".

### Apex, ALIAS e ANAME

Alguns registradores não deixam criar `CNAME` no domínio raiz. Para isso existem `ALIAS` e `ANAME` apontando para `SEU-USUARIO.github.io`, quando o registrador os suporta. Se não suportar, use os quatro registros `A`.

### Como o `concurrency` ajuda

O workflow gerado usa `concurrency` com `cancel-in-progress: false`: dois pushes seguidos não se atropelam no deploy.

### Cache e "não atualizou"

Depois de um deploy, o navegador pode mostrar a versão antiga por causa do cache. `Ctrl+Shift+R` recarrega sem cache. Se o arquivo mudou e o endereço dele não, é o cache.

</Camada>

<Camada tipo="armadilhas">

### Publicar a pasta errada

Tudo que está na pasta publicada fica público: `.env`, anotações, rascunhos. Publique uma pasta própria (como `dist/` ou `site/`), nunca a raiz do projeto inteira.

### Caminho-base esquecido

A página abre sem estilo e sem imagens porque os links começam com `/`. Num site de projeto, confira o caminho-base do framework.

### Segredo no JavaScript do site

Qualquer valor embutido no build é legível. Mova a chamada que usa o segredo para uma função no servidor.

### Esperar o DNS "na hora"

Registro novo leva tempo. Se `nslookup` ainda mostra o endereço antigo, espere, não apague nem refaça.

### Cadeado quebrado por conteúdo misto

Um único `http://` num site HTTPS derruba o cadeado. Procure por `http://` no código.

### Usar o GitHub Pages para vender

A doc não permite uso como hospedagem gratuita de negócio comercial. Para loja ou SaaS, use hospedagem apropriada.

### Voltar atrás na Netlify e esquecer o push seguinte

Com publicação automática ligada, o próximo push sobrescreve o rollback. Pause a publicação automática enquanto investiga.

### Achar que o rollback conserta o código

Ele só faz o site público voltar à versão anterior. O código quebrado continua no repositório. Reverta o commit também.

</Camada>
