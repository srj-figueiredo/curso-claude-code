## Essencial

Toda sessão do Claude Code começa do zero: ele não lembra de ontem. O que dá continuidade ao trabalho é a **memória**: arquivos que ele lê sozinho antes de você digitar a primeira palavra. Bem usada, ela troca "toda vez eu explico de novo" por "escrevi uma vez".

### Duas memórias, dois autores

| | **CLAUDE.md** | **Memória automática** |
|---|---|---|
| Quem escreve | Você | O Claude |
| O que contém | Instruções e regras do projeto | Preferências, correções e contexto que o código não mostra |
| Alcance | Projeto, usuário ou organização | Um repositório, compartilhado entre os worktrees dele |
| Quando carrega | Toda sessão | Toda sessão (só as primeiras 200 linhas ou 25 KB do índice) |

A documentação faz um aviso que vale decorar: **as duas são contexto, não configuração imposta.** O Claude lê e tenta seguir, mas não há garantia. Se algo **precisa** acontecer sempre, como rodar os testes antes de cada commit, o caminho é um *hook*, que executa por conta própria (o [M9](../m9/) ensina). CLAUDE.md orienta; hook obriga.

### Onde o CLAUDE.md mora

Há quatro lugares, do mais amplo ao mais específico. Todos são lidos e **somados** (um não anula o outro), e os mais específicos entram por último.

| Escopo | Arquivo | Para quê | Vai para o git? |
|---|---|---|---|
| **Organização** | Arquivo de política no sistema (ex.: `C:\Program Files\ClaudeCode\CLAUDE.md` no Windows) | Regras da empresa | Distribuído pela TI |
| **Usuário** | `~/.claude/CLAUDE.md` | Suas preferências em todos os projetos | Não |
| **Projeto** | `./CLAUDE.md` ou `./.claude/CLAUDE.md` | O que o time inteiro precisa saber | **Sim** |
| **Local** | `./CLAUDE.local.md` | Suas preferências neste projeto | Não: ponha no `.gitignore` |

Três regras de carga:

1. O Claude lê o `CLAUDE.md` da pasta onde você abriu a sessão **e de todas as pastas acima dela**, da raiz para baixo. Quanto mais perto de você, mais tarde entra.
2. `CLAUDE.md` em **subpastas** abaixo da sua só entra quando o Claude lê, escreve ou edita um arquivo daquela subpasta.
3. Comentários HTML (`<!-- nota para quem mantém -->`) são removidos antes de o texto chegar ao Claude. Servem de anotação para humanos, sem gastar contexto.

Para conferir o que carregou, rode `/context all` e olhe a lista **Memory files**. Na nossa execução, um `CLAUDE.md` de oito linhas aparecia ali com 202 tokens.

### Gerar o primeiro com `/init`

Na pasta do projeto, dentro de uma sessão:

```text
/init
```

O Claude lê o código e escreve um `CLAUDE.md` com comandos de build e teste, estrutura e convenções que descobriu. Se já existe um, ele sugere melhorias em vez de sobrescrever. A documentação também descreve uma versão interativa, em várias fases, ligada pela variável de ambiente `CLAUDE_CODE_NEW_INIT=1`: ela pergunta quais artefatos criar (CLAUDE.md, skills, hooks) e mostra uma proposta antes de gravar. Não a executamos aqui.

Dois cuidados com o resultado do `/init`:

- **Ele pode escrever em inglês, mesmo num projeto em português.** No nosso laboratório saiu em inglês. Peça em português, ou traduza.
- **É um rascunho.** Ele descreve o que viu, e boa parte é coisa que o Claude veria de novo sozinho. Enxugue.

### O que escrever (e o que não escrever)

A regra de ouro cabe numa frase: **escreva o que você explicaria de novo a cada sessão.** A documentação dá quatro gatilhos para adicionar uma linha:

- o Claude errou a mesma coisa pela segunda vez;
- uma revisão de código pegou algo que ele devia saber deste projeto;
- você digitou a mesma correção que digitou na sessão passada;
- uma pessoa nova no time precisaria do mesmo contexto.

O que entra: **comandos** (como testar, como subir), **convenções que fogem do padrão**, **decisões e seus motivos**, **armadilhas**. O que não entra: tudo que o Claude lê no código em dois segundos (lista de pastas, dependências, resumo da arquitetura) e procedimentos longos de várias etapas, que são trabalho para uma *skill* ([M8](../m8/)).

Para as frases funcionarem, faça-as **verificáveis**:

| Vago | Verificável |
|---|---|
| "Formate o código direito" | "Use indentação de 2 espaços" |
| "Teste suas mudanças" | "Rode `npm test` antes de commitar" |
| "Mantenha os arquivos organizados" | "Os handlers da API ficam em `src/api/handlers/`" |

E mantenha curto: **menos de 200 linhas por arquivo.** Arquivo maior gasta contexto e reduz a obediência. Instruções contraditórias são pior: o Claude pode escolher uma ao acaso.

<Nota rotulo="Resultado do nosso teste A/B (Ficha 1)">
Pedimos a mesma tarefa, "adicione o comando limpar", com e sem um CLAUDE.md. Em ambos os casos o Claude atualizou o README e manteve o `console.log` só na CLI, porque deduziu isso do código. O que mudou foi só a regra que não dava para deduzir: a mensagem de sucesso começar com "Pronto:". **CLAUDE.md vale pelo que o código não diz.**
</Nota>

### Importar arquivos e manter o pessoal fora do git

Um `CLAUDE.md` pode puxar outro arquivo com `@caminho`:

```text
Veja @README para a visão geral e @package.json para os comandos npm.
- Fluxo de git: @docs/git-instructions.md
```

O arquivo importado entra **inteiro** no contexto, junto com o CLAUDE.md que o chamou. Importar organiza, mas **não economiza** contexto. Para mencionar um caminho sem importar, coloque-o entre crases.

Para preferências suas que não devem ir ao time, crie `CLAUDE.local.md` na raiz do projeto e inclua-o no `.gitignore`. Ele é lido junto com o `CLAUDE.md`, logo depois dele.

### Quando um arquivo só não basta

Quando o `CLAUDE.md` cresce, a saída não é escrever mais fino: é **dividir por quem precisa**.

| Instrução | Onde fica |
|---|---|
| Vale sempre, em todo o projeto | `CLAUDE.md` |
| Vale só para alguns arquivos (ex.: os da API) | **Regra com caminho**: um `.md` em `.claude/rules/` com `paths:` no cabeçalho. Só carrega quando o Claude mexe num arquivo que casa |
| É um procedimento com etapas, chamado de vez em quando | **Skill** ([M8](../m8/)) |
| Precisa acontecer sempre, sem depender do Claude | **Hook** ([M9](../m9/)) |

Uma regra com caminho tem este formato:

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# Regras da API
- Todo endpoint valida a entrada.
- Use o formato padrão de erro.
```

### Repositório que já tem `AGENTS.md`

O `AGENTS.md` é um arquivo de instruções usado por outros agentes de código. O Claude Code o lê, com a ressalva de que **por padrão só quando não há nenhum `CLAUDE.md`** na sua pasta nem acima dela:

| O repositório tem | O Claude lê |
|---|---|
| Só `AGENTS.md` | O `AGENTS.md` |
| `AGENTS.md` e `CLAUDE.md` | Só o `CLAUDE.md` |
| `CLAUDE.md` que importa o `AGENTS.md` | O `CLAUDE.md`, com o `AGENTS.md` incluído |

Para dividir uma fonte única entre ferramentas, faça o `CLAUDE.md` importar o `AGENTS.md` e acrescentar só o que é do Claude.

### A memória automática

Além do que você escreve, o Claude **anota por conta própria**, em quatro tipos: `user` (seu papel e preferências), `feedback` (correções e acertos confirmados), `project` (decisões e prazos que o código não mostra) e `reference` (onde achar informação fora do projeto). Ele pula o que consegue derivar do código e o que seu CLAUDE.md já diz, e não grava em toda sessão.

Os arquivos ficam em `~/.claude/projects/<projeto>/memory/`: um índice `MEMORY.md`, com uma linha por memória, e um arquivo por tópico. **Só as 200 primeiras linhas (ou 25 KB) do índice entram no começo da sessão**; os arquivos de tópico o Claude lê sob demanda. É texto comum: você lê, edita e apaga.

Dois pedidos parecem iguais e vão para lugares diferentes:

| Você diz | Vai para |
|---|---|
| "Lembre-se: usamos pnpm" | Memória automática |
| "Adicione isto ao CLAUDE.md" | `CLAUDE.md` |

O comando **`/memory`** lista os arquivos de memória de usuário e de projeto, liga e desliga a memória automática e abre a pasta dela. Fica no seu computador: não vai para outra máquina nem para sessões na nuvem.

### Memória e compactação

O que acontece com cada coisa quando a conversa é compactada ([M2](../m2/)):

- **`CLAUDE.md` da raiz e regras sem `paths:`**: relidos do disco.
- **Memória automática**: relida do disco.
- **`CLAUDE.md` de subpastas e regras com `paths:`**: voltam sob demanda, quando o Claude tocar nos arquivos deles de novo.
- **Instrução dita só na conversa**: vira resumo e pode perder força.

Daí a regra do módulo anterior: instrução que precisa durar vai para o arquivo.

### A pasta `.claude`

O `.claude/` do projeto guarda a configuração que vai para o git; o `~/.claude/` guarda a pessoal. Quase todo mundo só mexe em dois arquivos: `CLAUDE.md` e `settings.json`. O resto é opcional, e o mapa é este:

| Você quer | Mexe em |
|---|---|
| Dar contexto e convenções | `CLAUDE.md` |
| Permitir ou bloquear ferramentas, rodar scripts em eventos | `settings.json` (`permissions`, `hooks`) |
| Guardar ajustes pessoais fora do git | `settings.local.json` |
| Criar um comando ou capacidade chamada com `/nome` | `skills/<nome>/SKILL.md` |
| Definir um subagente com ferramentas próprias | `agents/*.md` |
| Conectar ferramentas externas por MCP | `.mcp.json` |

Os [M7](../m7/) a [M10](../m10/) e o [M12](../m12/) abrem cada um.

### Em projeto grande

Num monorepo, um `CLAUDE.md` único na raiz ou engorda demais ou fica genérico. A documentação recomenda **dois níveis**: a raiz com o que vale em todo lugar (padrões de código, convenção de commit), e um `CLAUDE.md` por pacote ou subsistema com o que é daquela área. Se você abre o Claude em `packages/api/`, ele lê o da raiz e o da API, e nada de `packages/web/`. Se o `CLAUDE.md` de outras equipes atrapalha, a configuração `claudeMdExcludes` pula os que você escolher.

<Camada tipo="capo" titulo="Limites, carga e detalhes">

### Tamanhos que importam

- **Arquivos carregados na abertura** (CLAUDE.md, regras sem `paths:`): o Claude recebe o arquivo inteiro, desde que tenha até 4 MiB. Acima disso, nenhum trecho entra. A meta de 200 linhas é de **adesão**, não de limite técnico.
- **Arquivos carregados sob demanda** (CLAUDE.md de subpasta, regras com `paths:`): têm limite por arquivo, de 40.000 caracteres numa janela de 200 mil tokens. Em janela de 1 milhão, o limite é de 150.000 caracteres nos modelos mais novos. O que passa disso chega cortado, com um aviso para o Claude ler o resto. `wc -m arquivo` conta os caracteres.
- **`MEMORY.md`**: 200 linhas ou 25 KB, o que vier primeiro. O que passa não carrega.

### O aviso de tamanho

Se um arquivo de instruções passar do tamanho recomendado, aparece um aviso na abertura e no `/status`. Cada `CLAUDE.md`, arquivo de regra e importação conta como um arquivo.

### Outras pastas e hooks de diagnóstico

Pastas adicionadas com `--add-dir` **não** têm o `CLAUDE.md` carregado por padrão. Para carregá-lo, defina `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`. Para ver quais arquivos carregaram, quando e por quê, o hook `InstructionsLoaded` registra cada carga.

### Instruções do próprio Claude Code competindo com as suas

O Claude Code traz regras próprias de commit e de PR. Se o seu CLAUDE.md define outras, desligue as embutidas com `includeGitInstructions` e ajuste o texto de atribuição com `attribution` (veja o [M4](../m4/)).

### Importação externa

Importar de fora da pasta de trabalho (como `@~/.claude/minhas-regras.md`) numa memória de **projeto** abre uma janela de aprovação na primeira vez. Se você recusar, a importação fica desligada. Arquivos do seu `~/.claude` não pedem aprovação.

### Subagentes e memória

A memória automática da conversa principal **não** vai para subagentes. Um subagente pode ter uma memória própria, em pasta separada, se a configuração dele permitir.

### Desligar a memória automática

Ela vem ligada nas sessões locais. Desligue pelo `/memory` (salva `autoMemoryEnabled` em `~/.claude/settings.json`), por projeto com `autoMemoryEnabled: false`, ou com a variável `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Em sessões iniciadas por outro Claude e em sessões em segundo plano, o interruptor só desliga: não religa.

</Camada>

<Camada tipo="armadilhas">

### CLAUDE.md virando manual

Cada linha que o Claude já deduz do código é ruído que dilui as que importam. Corte lista de pastas, dependências e resumos de arquitetura.

### Frases vagas

"Escreva código limpo" não verifica nada. Troque por regras que um revisor consiga checar.

### Instruções contraditórias

Dois arquivos pedindo coisas opostas (um manda 2 espaços, outro manda tabs) fazem o Claude escolher ao acaso. Revise o conjunto de tempos em tempos, e use o `/doctor prompt-audit`.

### Editar o CLAUDE.md e esperar efeito na hora

O arquivo é lido na abertura. A versão nova entra no `/clear`, no `/compact` ou num reinício, como o [M2](../m2/) mostrou.

### Esperar obediência de ferro

É contexto. Para impedir uma ação, regra de permissão ou hook; para exigir uma, hook.

### Segredo no CLAUDE.md

O arquivo vai para o git. Chave, senha e token nunca entram ali ([M4](../m4/)).

### Pedir ao Claude para "lembrar" e achar que está no CLAUDE.md

"Lembre-se" grava na memória automática, que é só sua e só desta máquina. O que o time precisa saber vai para o `CLAUDE.md`.

### Testar um CLAUDE.md de subpasta pedindo ao Claude para criá-lo

O arquivo só carrega quando o Claude lê um arquivo daquela subpasta. Para testar, crie o arquivo você mesmo, pelo shell, e peça a leitura de um arquivo da pasta.

### Achar que o `AGENTS.md` sempre é lido

Basta existir um `CLAUDE.md` na pasta ou acima, mesmo um `CLAUDE.local.md`, para o `AGENTS.md` ser ignorado. Importe-o no `CLAUDE.md`.

</Camada>

</Gabarito>

<DeuErro>

- **A pasta de memória não existe.** A memória automática pode estar desligada. Em sessões iniciadas por outro Claude (por exemplo, uma chamada de `claude` pela ferramenta `Bash` de uma sessão) o interruptor só desliga. Abra uma sessão num terminal comum e use o `/memory`.

- **Não achei a pasta.** Ela só aparece depois da primeira gravação, e o nome da subpasta vem do caminho do projeto.
