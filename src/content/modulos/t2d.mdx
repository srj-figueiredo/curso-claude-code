O Seu Antônio chega numa segunda-feira com a cara fechada: "O computador do balcão não ligou. Eu perdi tudo?"

Se você respondeu "tem backup", ótimo, mas só se **já ensaiou** trazê-lo de volta. Esta estação fecha a Temporada 2 com o que separa um sistema que funciona na sua máquina de um sistema que dá para **entregar e confiar**: testar de verdade, guardar uma cópia, cuidar dos dados das pessoas e conduzir a entrega.

### Testar: o que a conferência cobre e o que ela não cobre

Ao longo da temporada, a conferência cresceu: **25** verificações (cadastro e painel), **61** (com login e papéis), **74** (com backup). Ela é a sua rede de segurança, e vale conhecer seus limites.

| A conferência **cobre** | A conferência **não cobre** |
|---|---|
| Cadastro, validação, filtro, status, painel | O visual: se a tela está bonita e legível em letra grande |
| Login, papéis, bloqueio, cookie, hash | O hábito do cliente: se a Clara entende o painel |
| Backup, restauração e recusa de arquivo falso | O computador real: se o sistema liga no PC da oficina |
| O que o Claude **pensou** em testar | O que ninguém pensou |

Por isso o teste tem três camadas: **a conferência automática** (rápida, repetível), **o seu uso à mão** (você é a primeira usuária ou o primeiro usuário) e **o uso do cliente** (a demonstração e o aceite). Uma não substitui a outra.

### Backup: a cópia que salva

Os dados da oficina estão **num arquivo**, o `dados/oficina.db`. Se o computador quebrar, o arquivo vai junto. O backup é uma **cópia datada** desse arquivo, guardada numa pasta à parte. Pedimos ao Claude:

- **`backup.mjs`**: copia o banco para `backups/oficina-AAAA-MM-DD-HHMM.db`, usando o próprio SQLite para que a cópia seja consistente, e **mantém só os 7 mais recentes** (a poda).
- **`restaurar.mjs`**: traz um backup de volta. Antes de trocar, **guarda uma cópia do banco atual** (`antes-da-restauracao-...`), e **recusa qualquer arquivo que não seja um banco válido**.

Repare nos dois cuidados do `restaurar`. Restaurar é uma operação perigosa: se você restaura o arquivo errado, **perde o que tinha**. Por isso ele guarda o atual antes e se recusa a aceitar lixo.

### O ensaio de desastre

Um backup que nunca foi restaurado é uma esperança, não um backup. Por isso o teste mais importante desta estação é **um ensaio**: fazer o backup, estragar de propósito, restaurar e ver os dados voltarem.

Fizemos, com o banco real de teste (as três ordens de exemplo):

| Passo | Resultado |
|---|---|
| `node backup.mjs` | `Backup criado: ...oficina-2026-11-13-2213.db` |
| Apagar uma ordem do banco | de 3 ordens para 2 |
| `node restaurar.mjs backups/oficina-...db` | "Banco restaurado". Ordens: **3** de novo |
| O banco de antes foi guardado? | Sim: `antes-da-restauracao-2026-11-13-2213.db` |
| Restaurar um arquivo de texto qualquer (`falso.db`) | **Recusado**, saída 1: "o arquivo não começa com o cabeçalho de um banco SQLite. Nada foi alterado" |

E o pior cenário: **apagamos o arquivo do banco inteiro** (`Remove-Item dados\oficina.db`) e restauramos a partir do backup. O banco voltou, com saída 0.

### Os dados das pessoas

O sistema da oficina guarda nome e telefone de clientes. O da Lia guarda nome e telefone de alunas. São **dados pessoais**, e no Brasil há uma lei sobre isso, a LGPD. Aqui não vamos fazer curso de Direito, mas vale levar quatro hábitos que reduzem muito o risco:

1. **Guarde só o necessário.** Se o sistema não precisa de CPF, não pergunte. Foi a primeira regra do briefing da oficina.
2. **Diga para quê.** Quem fornece o dado deve saber para que ele serve. Num formulário, uma frase curta e uma **caixa de aceite**: "Concordo em usar meu nome e telefone para agendar minha aula experimental."
3. **Permita apagar.** Se uma pessoa pedir para ter seus dados apagados, o dono do sistema precisa conseguir. Na agenda da Lia pedimos uma função que apaga os pedidos de uma aluna pelo telefone, e funcionou no teste real (`{"ok":true,"apagados":1}`).
4. **Proteja o que guarda.** Login, hash, `.env` fora do histórico e backup guardado com cuidado, já que o backup **também tem os dados**.

<Nota rotulo="Isto não é aconselhamento jurídico">
Esta página dá hábitos de bom senso, não parecer jurídico, e as regras de proteção de dados têm detalhes que dependem do caso. Quando o volume de dados, o risco ou o valor do contrato forem relevantes, consulte um profissional. Não verificamos o texto da lei em fonte oficial nesta data.
</Nota>

### Instalar no computador do cliente

O sistema roda **no computador da oficina**, sem internet. Para instalar, a pessoa precisa de quatro coisas:

1. **O Node.js** instalado no computador (a versão LTS, em nodejs.org).
2. **A pasta do sistema** copiada para o computador (sem a pasta `dados/` de teste).
3. **O `.env`**, criado a partir do `.env.example`, **com senhas que o cliente escolhe**.
4. **Um jeito de ligar.** Abrir o terminal na pasta e rodar `node servidor.mjs`. Para o cliente não técnico, isso é pedir demais, e a solução comum é um **arquivo de atalho** que faz isso com dois cliques.

Esse atalho, no Windows, é um arquivo `iniciar.cmd` com quatro linhas:

```text
@echo off
cd /d "%~dp0"
echo Oficina Boa Estrada: mantenha esta janela aberta enquanto usar o sistema.
node servidor.mjs
pause
```

<Nota rotulo="Não testado">
Tentamos executar o `iniciar.cmd` na nossa máquina de teste, mas o teste travou o terminal e não o repetimos. O conteúdo é padrão do Windows, mas **não foi verificado aqui**. Teste no computador do cliente antes de entregar, e anote em qual versão do Windows funcionou.
</Nota>

Duas perguntas que o cliente fará e que você precisa responder antes:

- **"E se eu quiser abrir de casa?"** O sistema atende só neste computador. Acesso pela internet exige hospedagem e outros cuidados, e tem custo que depende do fornecedor: consulte o preço atual no site de cada um antes de prometer.
- **"E se o computador estragar?"** É o backup. E onde ele fica: **numa pasta que não esteja só nesse computador** (um pendrive ou outro lugar). Combine com o cliente quem copia e com que frequência.

### Como vender isso

- **Venda o pacote completo.** "Sistema, manual, acessos, backup ensaiado e relatório" é um produto com começo e fim. "Faço um sistema" é uma promessa vaga.
- **Cobre à parte a manutenção.** Backup semanal conferido, troca de senha, ajuste de valores: serviço recorrente, claro e fácil de explicar.
- **Cuidado com o que prometer sobre dados.** Diga o que você fez (hash, login, backup) e o que depende do cliente (quem fica com o computador, a senha, a cópia).
- **Seja claro sobre o que não está no escopo.** Acesso pela internet, aplicativo no celular e integração com outros sistemas são outro projeto.

<Camada tipo="capo" titulo="Por baixo do capô: como o backup foi feito">

### Cópia consistente

O Claude usou o comando `VACUUM INTO` do próprio SQLite para gerar a cópia. Copiar o arquivo do banco "no braço" enquanto o sistema escreve pode produzir uma cópia quebrada. O `VACUUM INTO` pede ao banco que ele mesmo faça a cópia, de forma segura.

### A poda e as variáveis

O `backup.mjs` mantém os 7 backups mais recentes. As variáveis opcionais `BANCO` (caminho do banco) e `BACKUPS` (pasta das cópias) existem para o teste não tocar no banco real. Sem elas, os padrões valem (`dados/oficina.db` e `backups/`).

### A restauração por cópia e troca

O `restaurar.mjs` valida o arquivo (cabeçalho de banco SQLite e a tabela `ordens`), guarda o banco atual e só então troca, por cópia e renomeação. Se qualquer passo falha antes, **nada é alterado**.

### O `.gitignore` e o backup

Ele inclui `backups/`, porque o backup tem dados do banco e não deve ir para o histórico.

### O que ele avisou

Na nossa execução, o Claude listou o que decidiu sem o briefing dizer: a variável `BACKUPS`, a recusa de arquivo que não seja SQLite válido com a tabela de ordens e a recusa de sobrescrever um backup do mesmo minuto. São decisões de profissional que ele deixou claras para você revisar.

</Camada>

<Camada tipo="armadilhas">

### Backup na mesma pasta do banco, e só ali

Se o computador quebra, o backup vai junto. Copie para outro lugar, e combine quem faz.

### Nunca ter restaurado

O dia do desastre é o pior momento para descobrir que a restauração não funciona. Faça o ensaio.

### Restaurar o arquivo errado

Restaurar apaga o que tinha. O `restaurar.mjs` guarda o atual antes, mas confira o nome do arquivo.

### Guardar dado que o sistema não usa

CPF "por precaução" vira risco sem benefício. Pergunte só o que usa.

### Entregar com os dados de exemplo

As ordens EXEMPLO vão para o banco real do cliente. Apague antes.

### Prometer acesso de fora sem custo

Acesso pela internet tem custo e cuidados que mudam por fornecedor. Não prometa antes de consultar.

### Entregar o backup sem proteção

Ele tem os mesmos dados do banco. Guarde com o mesmo cuidado.

</Camada>

<Ficha
  id="t2d-e2"
  n={2}
  titulo="O ensaio de desastre"
  objetivo="Fazer backup, apagar o banco inteiro de propósito, restaurar e provar que os dados voltaram."
  minutos={30}
  pre="Ficha 1 e o sistema já usado uma vez (o banco existe)"
  versao="2.1.325"
>

1. Suba o sistema uma vez para criar o banco (`node servidor.mjs`), espere a mensagem "rodando" e desligue com <kbd>Ctrl</kbd>+<kbd>C</kbd>. Confirme que existe `dados/oficina.db`:

   <SO unix="ls dados" win="Get-ChildItem dados" />

2. Faça o backup e veja o arquivo criado:

   ```bash
   node backup.mjs
   ```

   <SO unix="ls backups" win="Get-ChildItem backups" />

3. **O desastre.** Apague o banco inteiro:

   <SO unix="rm dados/oficina.db" win="Remove-Item dados\oficina.db -Force" />

4. **A restauração.** Troque `NOME` pelo nome do arquivo que apareceu em `backups` (começa com `oficina-`):

   ```bash
   node restaurar.mjs backups/NOME
   ```

5. Suba o sistema de novo, entre e confirme que as ordens voltaram.
6. **O arquivo falso.** Crie um arquivo qualquer e tente restaurá-lo:

   <SO unix={`echo "texto qualquer" > falso.db`} win={`Set-Content falso.db "texto qualquer" -Encoding ascii`} />

   ```bash
   node restaurar.mjs falso.db
   ```

<Prova>

Os dados voltam e o arquivo falso é recusado. Na nossa execução, no PowerShell 5.1:

| Passo | Resultado |
|---|---|
| `node backup.mjs` | `Backup criado: ...\backups\oficina-2026-11-13-2220.db` e "Mantendo os 7 mais recentes" |
| Apagar `dados\oficina.db` | O arquivo deixou de existir |
| `node restaurar.mjs backups\oficina-...db` | "Banco restaurado a partir de...", saída 0, e `dados/oficina.db` **existe de novo** |
| `node restaurar.mjs falso.db` | "Recusado: falso.db o arquivo não começa com o cabeçalho de um banco SQLite. Nada foi alterado.", saída 1 |

Num teste anterior, com o banco ainda no lugar, o fluxo contou as ordens: **3** antes, **2** depois de apagar uma, **3** depois de restaurar, e o banco de antes foi guardado em `antes-da-restauracao-...`. Se o banco foi apagado por inteiro, não há "banco de antes" a guardar, e a restauração só recria.

</Prova>

<Gabarito>

O que esse ensaio prova é uma frase: "se o computador quebrar, eu sei trazer os dados de volta". Anote o tempo que levou. Esse número é uma boa informação para o cliente.

</Gabarito>

<DeuErro>

- **O `restaurar.mjs` recusa um backup de verdade.** Confira o nome: um erro de digitação vira "arquivo não existe". Copie o nome da lista.
- **Depois de restaurar, o sistema pede login e não aceita a senha.** O servidor recria os usuários a partir do `.env` ao iniciar. Confira que o `.env` está na pasta.

</DeuErro>
