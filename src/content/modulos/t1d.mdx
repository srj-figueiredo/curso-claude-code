A Marta abriu o site no celular dela e adorou. Duas perguntas na sequência: "E se eu pedir uma mudança amanhã e você estragar?" e "Como as pessoas veem isso? Eu posso mandar o endereço?"

Esta estação responde às duas. A primeira é sobre **voltar atrás** (git). A segunda, sobre **colocar no ar** (GitHub Pages). No meio, uma pergunta que quem está começando raramente faz: **o que não pode ir para a internet?**

### Pontos de salvamento: o git

Quem joga sabe o valor de salvar antes da fase difícil. O **git** é isso para um projeto. A cada marco, você registra um **commit**: uma foto da pasta inteira com um nome ("Primeira versão do site"). Se um dia algo quebrar, você volta para uma foto anterior, e o resto do trabalho continua lá.

O melhor é que você não precisa decorar comando. Peça ao Claude:

```text
Comece o controle de versão nesta pasta (git, branch main) e faça o primeiro commit com todos os arquivos, com uma mensagem clara em português.
```

Na nossa execução, ele fez em 3 passos o que normalmente exige uma sequência de comandos, e escreveu uma mensagem útil:

```text
3d27e40  Primeira versão do site da Doce Esquina

Adiciona a página única da confeitaria (index.html), o briefing com
os dados do cliente, o script de conferência (conferir.mjs) e as
instruções do projeto (CLAUDE.md).
```

Dois detalhes que podem aparecer:

- Um aviso sobre "LF para CRLF" no Windows. É só o computador ajustando como as quebras de linha são gravadas. Não impede nada.
- Uma linha `Co-Authored-By: Claude ...` no fim da mensagem. É uma assinatura que registra que o Claude ajudou. Pode ficar ou sair, conforme a política do seu trabalho.

### Errar sem medo: desfazer com o git

Agora a prova de valor. Estragamos o site de propósito: o título virou "DOCE" e o preço do bolo inteiro caiu de R$ 68,00 para R$ 6,80. O roteiro de conferência da T1B gritou na hora:

```text
(1) Todo preço em R$ do HTML aparece no briefing: FALHOU
3 de 4 itens OK
```

Aí o pedido:

```text
Mexi no index.html sem querer e quero desfazer. Volte o index.html para o último commit e confirme que o git não mostra mais nenhuma mudança.
```

O Claude voltou o arquivo, mostrou que o git estava limpo ("nothing to commit, working tree clean") e rodar a conferência de novo voltou a `4 de 4`. Um detalhe: ele **não rodou** o `conferir.mjs`, porque só tínhamos liberado comandos do git, e avisou isso. Era exatamente o comportamento certo: licença só para o que foi combinado.

Estas duas ferramentas (o roteiro de conferência e o git) trabalham juntas. A conferência avisa que algo quebrou. O git permite voltar.

### O que vai para a internet é público

Chegou a hora de publicar, e aqui mora o erro mais caro de quem está começando. Pense assim: **tudo o que você publica pode ser lido por qualquer pessoa**, inclusive o código-fonte da página. E o repositório inteiro no GitHub, se for público, também.

Olhe a pasta do projeto:

| Arquivo | Deve ir para a internet? |
|---|---|
| `index.html` (o site) | **Sim**: é o que o cliente vai mostrar |
| `briefing.md` | **Não**: tem dados do cliente e as regras da conversa |
| `CLAUDE.md` | Não: são as suas regras de trabalho |
| `conferir.mjs` | Não: é a sua ferramenta |

A solução simples: **separar o site numa pasta própria**. O GitHub Pages sabe publicar uma pasta chamada `docs`. Você pede:

```text
Quero publicar só o site, sem o briefing e os outros arquivos. Crie uma pasta docs e mova o index.html para dentro dela (use git mv). Ajuste o conferir.mjs e o CLAUDE.md para o novo caminho, rode node conferir.mjs, mostre o resultado e faça um commit.
```

Na nossa execução, ele fez tudo, a conferência continuou em `4 de 4` e ainda levantou uma questão certeira: "`briefing.md`, `CLAUDE.md` e `conferir.mjs` continuam rastreados na raiz do repositório. Se a publicação for só a pasta `docs/`, isso já basta. Se o repositório inteiro for publicado, esses arquivos ainda vão junto."

Repare no que isso significa: mesmo publicando só a pasta `docs`, **o repositório do GitHub continua público e visível**, com o briefing dentro. Para o curso, o cliente é fictício e não faz mal. Para um cliente real, escolha uma de duas saídas: um **repositório só com o site** (o briefing fica fora), ou um repositório **privado**. Antes de escolher o privado, confira se o seu plano do GitHub permite o Pages em repositório privado: nem todo plano permite.

### Colocar no ar

Com o site separado, são três passos:

1. **Enviar o repositório ao GitHub.** Você precisa de uma conta e do programa `gh` (o [guia "Git e GitHub do zero"](../m4/) ensina). Depois, peça ao Claude: "Crie um repositório público no meu GitHub chamado doce-esquina e envie este projeto para lá."
2. **Ligar o Pages.** No GitHub, abra o repositório: **Settings**, **Pages**, em **Build and deployment** escolha **Deploy from a branch**, depois a branch `main` e a pasta `/docs`, e clique em **Save**.
3. **Esperar uns minutos e abrir o endereço**, que tem este formato:

```text
https://SEU-USUARIO.github.io/doce-esquina/
```

Sua página só tem um arquivo e nenhum caminho relativo, então funciona dentro de `/doce-esquina/` sem ajuste. O [guia "Do computador para a internet"](../m5/) explica o que muda quando o site cresce.

<Nota rotulo="Cuidado: vitrine ou loja?">
Os termos do GitHub não permitem usar o Pages como hospedagem gratuita para um negócio comercial. Uma página-vitrine de portfólio ou demonstração é uma coisa; o site oficial de uma confeitaria que recebe pedidos é outra. Para clientes reais, leia os termos e considere uma hospedagem própria (o [guia "Do computador para a internet"](../m5/) discute as opções).
</Nota>

### O pacote de entrega

Quando você entrega o trabalho, entrega um pacote, não só uma página:

- o **endereço** do site no ar;
- o **repositório**, com todo o histórico (o cliente é dono do que pagou);
- o **CLAUDE.md**, para quem for mexer depois;
- o **conferir.mjs**, a prova de que o site cumpre o combinado.

Isso é o que separa "alguém que fez uma página" de "um profissional que entrega um sistema que dá para manter".

### Como vender isso

- **Mostre o pacote, não só o link.** "Seu site está no ar, o histórico está guardado e dá para voltar atrás se algo quebrar" justifica o valor e dá confiança.
- **Ofereça manutenção.** Atualizar preços e horários todo mês, com conferência, é um serviço recorrente e fácil de explicar.
- **Seja claro sobre os custos.** O Pages é grátis. O domínio próprio (`www.doceesquina.com.br`) tem custo anual, e quem paga deve estar combinado desde o início. O [guia "Do computador para a internet"](../m5/) mostra como funciona.
- **Informe o que a IA fez.** Alguns clientes querem saber. A transparência é uma vantagem competitiva, não um problema.

### Três lugares

O git trabalha com **três lugares**: a pasta onde você edita, uma "sala de espera" onde você escolhe o que vai no próximo commit, e o histórico. O [guia "Git e GitHub do zero"](../m4/) desenha esse modelo mental e mostra branches, conflitos e como recuperar um commit perdido.

### Por que o Claude consegue operar o git

Ele roda os comandos do git por você, e cada um passa pela permissão. Na nossa execução, liberamos `Bash(git *)`. Como o `*` cobre qualquer subcomando do git, é uma liberação ampla: a Temporada 2 explica como liberar só `git log` ou `git status`.

### O que o GitHub Pages faz

Cada vez que você envia mudanças, o GitHub atualiza o site a partir da pasta escolhida. O endereço não muda.

</Camada>

<Camada tipo="armadilhas">

### Publicar o repositório com o briefing

Quando o repositório é público, o briefing do cliente também é. Separe o site ou use um repositório só com ele.

### Commits sem nome

"Atualização" não ajuda ninguém. Peça ao Claude mensagens que digam o que mudou e por quê.

### Esquecer de fazer o commit antes de uma mudança grande

O ponto de salvamento só ajuda se existir. Faça um commit antes de pedir algo grande.

### Achar que o git guarda tudo

Ele guarda o que foi commitado. Mudanças que você não salvou voltam a se perder se você pedir para descartar.

### Pages que "não atualiza"

Às vezes o navegador guarda a versão antiga. Recarregue com <kbd>Ctrl</kbd>+<kbd>F5</kbd> e aguarde alguns minutos.

### Usar o GitHub Pages para um negócio comercial

Leia os termos do GitHub antes de usar o Pages no site oficial de um cliente que vende pela página.

</Camada>

### A reunião de entrega, em 15 minutos

Entregar é uma conversa curta e planejada, não um "está aí o link". Roteiro:

1. **Abertura (1 min).** "Hoje eu te mostro o site no ar e combino o que vem depois."
2. **Demonstração (5 min).** Abra o site no celular **dela**, não no seu. Peça que ela mesma teste o botão do WhatsApp e o formulário. Quem usa se convence mais que quem assiste.
3. **O que foi feito e como conferi (3 min).** Leia o relatório de entrega, incluindo o que ficou de fora.
4. **Como pedir mudanças (2 min).** Mostre o manual do site e o prazo combinado.
5. **Aceite (2 min).** Peça que ela confirme por escrito (modelo abaixo).
6. **Fechamento (2 min).** Combine um contato de acompanhamento para uma semana depois.

Modelo de **termo de aceite**, curto e em linguagem simples:

```text
Eu, Lia, aceito a entrega do site do Studio Lia, versão 1, no endereço (cole o endereço).
Conferi o formulário de aula experimental e o botão do WhatsApp no meu celular.
Pendências combinadas: valor do plano trimestral (a Lia informa) e texto de boas-vindas (a aprovar).
A manutenção combinada é: (descreva o que está incluído e o prazo).

Data: ___/___/_____        Assinatura ou resposta "aceito" por mensagem: ____________
```

<Nota rotulo="Isto não é aconselhamento jurídico">
Os modelos desta página são pontos de partida. Contrato, termos de uso, proteção de dados do cliente e dos clientes dele (LGPD) e propriedade do domínio merecem a orientação de um profissional quando o valor ou o risco forem relevantes.
</Nota>

### Quem é dono do quê

Combine, antes de publicar, quem é dono de cada peça. É o ponto que mais gera conflito depois:

| Peça | Recomendação |
|---|---|
| **O domínio** (`studiolia.com.br`) | Registrado no **nome e e-mail de quem contratou**. Você acessa se houver autorização. |
| **O repositório e a publicação** | Na conta de quem contratou, ou transferido para ela ou ele na entrega. |
| **Senhas e acessos** | Nunca por mensagem de texto. Use o gerenciador de senhas ou peça que a própria pessoa crie as contas. |
| **O código e o conteúdo** | Combinados por escrito: ela pode usar, e você pode (ou não) usar no portfólio. |

### Você domina a Temporada 1 se consegue

Responda **sem olhar a página**, em voz alta, como se explicasse a quem contratou você:

1. O que o Claude Code faz que o chat não faz?

3. O que você faz antes de construir, e por quê?
4. Como prova que o trabalho está pronto? O que a sua conferência não pega?

6. Como desfaz um erro? Por que o briefing não vai para a internet?
